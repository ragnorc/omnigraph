## Lessons from earlier runs

From the queue's memories and the four earlier runs:

- Main had no new commits, so the whole run went to the gaps the last runs listed: S3 faults during merges and schema apply, served optimize resume over several tables, and cleanup during reads (#958). Real embedding providers stay open: the box holds no provider key.
- False alarms to avoid: f32 vector precision, loads that omit a property (#1278), documented `409` read-set conflicts and optimize refusals under load, set semantics of an unbound traversal, refused reads of commits on deleted or recreated branches.
- Direct-root setup needs `cluster force-unlock` after a direct `cluster apply` before a server starts (#1359).

This run found two new false alarms, both in its own scripts:

- `cleanup` from one process while other CLI processes write, merge and create or delete branches on the same graph is outside the supported topology: cleanup and branch creation and deletion keep the single-writer-process boundary (docs/dev/invariants.md, "Current support boundaries"). Under that setup cleanup was refused every time a write landed during its capture ("collector branch 'main' changed during capture; retry cleanup": 0 of 10 cleanups completed beside a writer committing 16 times a second, 9 of 10 at 3 a second), and merges met `read_set_conflict` with `effects: none`. Both are documented refusals; the two scripts were removed.
- `resume_at` skips a table deferred for `resource_limit`: the engine sets it only for run-wide bounds, by design (`DeferReason::ResourceLimit`). The documentation consequence is the first finding below.

| `og-stress-reconcile-without-actor-reports-unknown` | After a server was killed during an accepted deployment whose graph had started, the documented reconciliation (`cluster apply --deployment-id ID --writers-stopped`, no `--as`) fails on a graph with a policy: `deployment_outcome_unknown`, "no actor for engine-layer policy check ... almost certainly a bug", and a new admission lock is retained. The guide says successive bounded runs reach every table and that `resume_at` names the first deferred table, and it does not mention the implicit ceiling. A documentation issue | 3 |

## Lessons applied

The queue's memories and the five earlier runs gave these rules:

- Spend time on the commits merged since the last run. Here those were the streamed merge validation (#1433), lost conditional races (#1426), direct writes under the applied policy (#1423) and one policy binding rule (#1434).
- Avoid the known false alarms: f32 vector precision, loads that omit a property (#1278), documented `409` and optimize refusals, set semantics of an unbound traversal, refused reads of commits on deleted branches, and cleanup beside other writer processes.
- Count every maintenance refusal as a result to explain. The new finding came from `index build` refusals that `ufuzz.py` had counted as allowed refusals.

This run found two new false alarms, both in its own scripts:

- `omnigraph access` does not report `reclaim`, by design ("It does not report `reclaim`, since no server route runs cleanup"). A direct `cleanup` is still judged by the policy, so a script must judge `reclaim` from the policy itself.
- A staged merge can need more than two stages. When half of a branch still holds more than 32 MiB of keys, the first stage is refused too, as the guide says.

## Findings

| Queue slug | Finding | Priority |
|---|---|---|
| `og-stress-vector-index-after-column-patch-blocks-index-build` | After an `update` of a vector property under `@index` takes the column-patch route (the type has a Blob or vector column that the update leaves out), every later `index build` on the branch fails with "the statistics of vector index 'v_idx' name no partition count". `optimize` reports the table as failed with the same message. The btree and full-text indexes of the type cannot be built either, because they share the batch. More writes, a full-text rebuild and more optimize runs do not clear it, and schema migration refuses to drop the `@index`. `nearest` still answers correctly, by a scan. Cause: after the column patch, Lance keeps `v_idx` with an empty fragment bitmap, and its statistics name no `num_partitions` (`index_type: "N/A"`). `index_fold_batch` calls `vector_partition_count` (`crates/omnigraph/src/table_store.rs`), which makes the missing count an error for the whole batch. The v0.15.0 release fails the same way. Workaround: export the type and reload it with `load --mode overwrite` | 2 |

The finding stays in the findings queue. It is priority 2 because a workaround exists, so it was not promoted to GitHub. The reproduction is [repros/vector_partition_count.sh](../../tools/stress/repros/vector_partition_count.sh). `ufuzz.py` hit it in 4 of 60 seeds, and `vminimize.py` reduced one seed to four commands.

- `og-stress-server-boot-refusal-keeps-lock`: a refused start leaves the lock, and the next start fails with `state_lock_held`.
- `og-stress-reconcile-without-actor-reports-unknown`: the documented reconciliation without `--as` still reports `deployment_outcome_unknown`.
