# The released v0.16.0 CLI against EDITION-2

`REPO_SLUG=ModernRelay/omnigraph VERSION=v0.16.0 bash scripts/install.sh`
installed `omnigraph 0.16.0`, channel `stable`, commit
`00b8cca842f2bf009bebeefcf765672b5ff64b26`, which writes storage format 17
and serves 14 to 17. EDITION-2 (the CLI built at
`EDITION_2_SOURCE_COMMIT` 9ad7c8ef) is `0.16.1`, writes 18 and serves 14 to
18; neither reports `gq_language`.

The harness ran the generated worlds of seeds 1000..1099 (100 worlds,
2,400 cases, generator v1) with v0.16.0 in the edition-2 slot and EDITION-2
in the other, each binary initializing and loading its own graph:

| Result | Cases |
|---|---|
| same status, same error code, same rows, columns and types | 2,350 |
| `types` reported as different | 49 |
| same rows in another order under `order` | 1 |

The 49 `types` rows were the comparator's own fault at the time: it renamed
a `<binding>._score` type on one side only, while both binaries returned the
identical `d2._score: F32` (fixed since in `harness/classify.py`, which now
renames types only where it renamed the columns). The one reordered result
orders by a key on which every reordered row ties (`i2.rank` 2.5, 1.5,
0.5; contract `D10`). So v0.16.0 accepts and answers what EDITION-2 does on
this sample; no difference between them was found.
